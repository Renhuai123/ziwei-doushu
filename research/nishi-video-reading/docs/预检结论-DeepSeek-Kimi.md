# 预检结论（2026-11-08，DeepSeek 实调 + Kimi 估算接口）

原帧：P13 第 51848 帧（AV1 1620×1080）、P25 第 39498 帧（H.264 1620×1080）、P48 第 49899 帧（H.264 1920×1080），均从腾讯云全帧取回、与清单 sha256 一致。每张切 6 种输入，共 18 张。明细见 `结果.md`、`Kimi估算.md`。

## 每张图的 token

| 输入 | DeepSeek（实调，关思考） | Kimi K3.1 Pro（估算接口） |
|---|---|---|
| 整帧 1620×1080 | 977 | 2,272 |
| 整帧 1920×1080 | 968 | 2,701 |
| 整帧 + detail=low | 约 190（缩到 512） | 2,272 / 2,701（Kimi 忽略 detail） |
| 四分之一块 810×540 / 960×540 | 275 / 314 | 588 / 708 |
| 544×544 | 184 | 408 |
| 700×700 | 308 | 633 |
| 300×300 | 184（被放大到约 544²） | 129（不放大） |

- DeepSeek 18 张全部答出了画面内容（「老师黑板前讲课」「水火既济卦象图」等），没有一张没看到图。
- DeepSeek 原尺寸下约 1,600–1,800 像素 / token；1620×1080 整帧几乎不被缩小（1.75M 像素 → 约 1.69M）。
- Kimi 约 770 像素 / token，同一张图约是 DeepSeek 的 2.3 倍 token；700×700 手部裁片 = 整帧的 28%，与 Fable 推算一致。

## 对方案的影响

1. **逐帧层（DeepSeek）**：每帧约 977 token，与方案假设的 1,024 基本一致。160 万帧图片输入约 15.7 亿 token，非高峰 ¥1/M ≈ ¥1,570，加输出与上文，Fable 估的约 ¥2,300 成立（小考后按冻结格式重算）。
2. **v3 第 3 节「2×2 分块，每块不大于 544×544」要修正**：544 正好在放大门槛上，544 块并不会被放大；1620×1080 整帧的四块加起来（4×275=1,100）和整帧（977）几乎同价同清晰度。想让 DeepSeek「放大看粉笔小字」，裁片要明显小于 544（如 300–400 像素），代价是块数变多。这一条在小考实验 3（整帧 vs 分块）里一并量准确率再定。
3. **Kimi 不能读全量**：整帧 2,272 token × ¥13/M ≈ ¥0.03 / 帧，160 万帧约 ¥4.7 万（批量六折约 ¥2.8 万），确认只读字幕句层和板面层的关键画面，且优先发裁片（700 方块只要 28%）。
4. **全量取图可以不经本机**：DeepSeek 支持直接给图片网址（60 秒内下载、单图 ≤32 MiB），全量时可用腾讯云私有桶的临时签名网址让它直接取图（会产生腾讯云外网流量费，试点时量）。

花费：DeepSeek 19 次请求约 1.2 万 token，约 ¥0.01；Kimi 估算接口不计费。
